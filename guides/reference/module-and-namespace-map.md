# Module and Namespace Map

This guide lists every documented `Jido.*` module, the namespace that owns it, and the layer each namespace belongs to. Use it to find where a concept lives. For function-level lookup, see the [Public API Guide](public-api-reference.md).

The package is one Mix project and one OTP application, `:jido`. It compiles 521 modules. This guide lists the 221 with a module document. The other 300 set `@moduledoc false`, or are generated by a DSL, and are private: do not call them, because they can change or disappear in any commit.

## Layers

Each namespace belongs to one layer, and a module can depend only on lower layers. The repository's architecture check enforces this order. It also forbids `Jido.Agent` from calling `Jido.AgentServer`, so an Agent stays pure data and can run without a process.

| Layer, lowest first | Namespaces |
| --- | --- |
| Primitives | `Jido.Id`, `Jido.Joi`, `Jido.Expr`, `Jido.Error`, `Jido.Trace`, and the Codec term, document, encoder, error, and issue modules |
| Value model | `Jido.Signal`, `Jido.Signal.Codec`, `Jido.Signal.Context`, `Jido.Session`, `Jido.Thread`, `Jido.Catalog` and its value modules, and `Jido.Codec` with its contract, reference, and value modules |
| Definitions | `Jido.Action`, `Jido.Flow`, `Jido.Instruction`, `Jido.Plugin.Config`, `Jido.Signal.Catalog`, `Jido.Signal.Router` |
| Execution | `Jido.Exec`, `Jido.Telemetry.Exec` |
| Agent domain | `Jido.Agent`, `Jido.Plugin`, and the Plugin context, init, and input modules |
| Live runtime | `Jido`, `Jido.AgentServer`, `Jido.Persistence`, `Jido.Signal.Bus`, `Jido.Signal.Dispatch`, `Jido.Telemetry`, `Jido.Telemetry.AgentServer`, `Jido.Telemetry.Signal`, `Jido.Trace.Context` |
| Capabilities | `Jido.AI`, `Jido.Telemetry.AI`, and the bundled Plugins: `Jido.Plugin.Audit`, `Jido.Plugin.Bus.Client`, `Jido.Plugin.Bus.Manager`, `Jido.Plugin.Timer`, `Jido.Plugin.SensorManager` |
| Composition | `Jido.Catalog.Discovery` and the application module |

A sub-module can sit in a different layer from its parent. For example, `Jido.Signal` is in the value model while `Jido.Signal.Bus` is in the live runtime.

## Process trees

The application starts one supervisor with these children. Names below are private unless a table in this guide lists them.

```text
Jido.Supervisor (one_for_one)
├── Registry named Jido.Signal.Registry
├── Task.Supervisor named Jido.Exec.TaskSupervisor (max_children: :infinity)
├── Jido.Catalog.Discovery (a temporary task that runs one scan)
├── Jido.Telemetry.AI.CorrelationStore
├── Jido.Instance.NamespaceRegistry
├── Jido.Persistence.ETS.Owner
└── Runic.Runner for direct and durable execution
```

The application starts no Agents and no instance. Each instance that you start with `Jido.start_link/1` or `use Jido` is a separate supervisor.

```text
Your instance, for example MyApp.Jido (one_for_one)
├── Runic.Runner for the instance
├── Task.Supervisor (max_children from :max_tasks)
├── Registration guard
├── Registry for Agent names
├── Runtime store
└── DynamicSupervisor for AgentServer activations
```

See [Instances and Tenants](../operations/configuration-and-tenant-isolation.md) for what an instance owns.
